CODE AREA 1: CROW FRAMEWORK & APPLICATION SETUP
========================================================
Topic: Web Server Architecture & Routing

Key points to explain:
- What is Crow?
    * C++ micro web framework inspired by Python Flask
    * Header-only library — just #include "crow.h"
    * Provides HTTP routing, request/response handling, template rendering

- Application initialization:
    * crow::SimpleApp app; — creates the HTTP app instance
    * crow::mustache::set_base("."); — sets root directory for HTML templates
    * app.bindaddr("127.0.0.1").port(18080).run(); — starts the server

- Routing with CROW_ROUTE macro:
    * CROW_ROUTE(app, "/login") registers a URL endpoint
    * Lambda function handles the request
    * .methods(crow::HTTPMethod::POST) restricts HTTP methods
    * Example: loading and rendering a login page template

- Mustache templating:
    * crow::mustache::context acts as a key-value map
    * ctx["title"] = "HOME | X-NCU"; passes data to HTML
    * Templates use {{variable}} syntax for dynamic content
    * Supports strings, booleans, integers, and vectors of contexts

- Libraries used:
    * crow.h — web framework
    * jwt-cpp/jwt.h — JWT tokens
    * sha256.h — password hashing
    * otp_service.h — OTP email verification
    * <fstream>, <sstream> — CSV file I/O


========================================================
CODE AREA 2: CSV-BASED DATABASE LAYER
========================================================
Topic: Data Storage & Retrieval using Flat Files

Key points to explain:
- Why CSV instead of a traditional database?
    * Lightweight, no external dependencies
    * Human-readable, easy to inspect and debug
    * Good for learning file I/O concepts

- Database architecture — 6 CSV files:
    * database/users.csv — 14 columns (UserID, Handle, Email, FullName,
      Role, Password hash, Bio, IsVerified, CreatedAt, Location, Link,
      FollowingCount, FollowersCount, Posts)
    * database/posts.csv — all posts
    * database/students.csv, teachers.csv, staff.csv — role-filtered posts
    * database/news.csv — trending news sidebar items

- CSV READ pattern (User Constructor):
    * Open file, skip header row with getline
    * Iterate row-by-row with while(getline)
    * Use stringstream + getline(ss, field, ',') to split columns
    * Match target ID, parse remaining fields
    * try-catch blocks guard against malformed data

- CSV WRITE pattern (Register User):
    * Open file in append mode (ios::app)
    * Auto-increment ID: scan all rows for maxId, newId = maxId + 1
    * Check if file ends with newline before appending (seekg(-1))
    * Write comma-separated fields including SHA-256 hashed password

- CSV UPDATE pattern (Save Post):
    * Read ALL lines into vector<string>
    * Find matching row by ID
    * Replace that row with updated data
    * Rewrite ENTIRE file (full-file rewrite approach)
    * Necessary because CSV has no random-access update capability

CODE AREA 3: USER & POST DATA MODELS (OOP)
========================================================
Topic: Classes, Encapsulation & Data Sanitization

Key points to explain:
- Object-Oriented Design principles applied:
    * Encapsulation — all data members are private
    * Overloaded naming — same function name for getter and setter
      e.g., id() returns the value, id(int val) sets it

- User class:
    * 14 private fields matching CSV columns exactly
    * Constructor takes targetUserNo, reads from CSV to populate fields
    * isFound_private flag indicates if user was located in database
    * Getter/setter pairs for every field

- Post class:
    * Fields: id, user_id, parent_id, content, likes_count,
      retweets_count, created_at, role, isFound
    * parent_id = -1 means top-level post (not a reply)
    * Static methods: getpost(int id) and savepost(const post &p)
      operate on CSV directly, not tied to an instance
    * Constructor creates AND saves the post in one step

- Input sanitization (critical for CSV integrity):
    * Newlines (\n, \r) replaced with spaces — prevents CSV row breaks
    * Commas replaced with semicolons — prevents CSV column shifts
    * Applied before any file write operation
    * Without this, user input could corrupt the entire database

- Post creation workflow:
    1. Sanitize input content
    2. Scan posts.csv for highest existing ID
    3. Calculate newId = maxId + 1
    4. Check if file needs trailing newline
    5. Look up author's role via user(user_id)
    6. Write new row with timestamp to CSV

CODE AREA 4: AUTHENTICATION & SECURITY
========================================================
Topic: JWT Tokens, SHA-256 Hashing, OTP Email Verification

Key points to explain:
- Authentication flow overview:
    * Login: Email + Password → SHA-256 hash check → JWT token → cookie → redirect
    * Signup: Email + OTP verification → register in CSV → JWT token → cookie → redirect

- SHA-256 password hashing:
    * Passwords NEVER stored in plaintext
    * sha256() function from external library
    * During login: hash the input, compare with stored hash
    * One-way function — cannot reverse hash to get password

- JWT (JSON Web Token) creation:
    * Issuer: "x-ncu"
    * Payload: user_id (as string)
    * Expiry: 24 hours from creation
    * Algorithm: HMAC-SHA256 with secret key
    * Token set as HttpOnly cookie — not accessible via JavaScript (XSS protection)

- JWT verification (called on every protected route):
    * Extract token from Cookie header
    * Fallback: check Authorization header (Bearer token)
    * Decode and verify issuer + algorithm
    * Extract user_id from payload
    * Returns user_id (>0) on success, -1 on failure

- OTP-based email verification:
    * Singleton pattern: OTPService::getInstance()
    * POST /send-otp generates and emails an OTP
    * POST /register verifies OTP before allowing registration
    * OTPs have expiry window — expired ones are rejected
    * Prevents fake/spam account creation

- Error handling table:
    * Login success → 303 redirect to home
    * Wrong password → 401
    * User not found → 404
    * Database error → 500
    * User already exists → 422
    * Invalid OTP → 401
    * Missing fields → 400

CODE AREA 5: API ROUTES & FEED RENDERING
========================================================
Topic: Endpoints, Feed Logic & Profile System

Key points to explain:
- Complete route map (GET endpoints):
    * / — Home feed (all posts)
    * /students, /teachers, /staff — role-filtered feeds
    * /login, /signup — auth pages
    * /logout — clear cookie, redirect to login
    * /profile/<handle> — user profile page
    * /about — static about page
    * /editprofile — edit profile form

- Complete route map (POST endpoints):
    * /auth — login authentication
    * /register — new user registration
    * /send-otp — send OTP to email
    * /post — create a new post
    * /updatepost — like or repost a post

- Home feed logic (step by step):
    1. Verify JWT token — redirect to /login if invalid
    2. Load current user context (name, handle, initials)
    3. Read all posts from posts.csv
    4. Count replies using unordered_map<int,int> (parent_id → count)
    5. Sort posts newest-first by post_id (descending)
    6. Build context for each post (author info, role badges, timestamps)
    7. Load news sidebar from news.csv
    8. Render index.html with all context data

- Role-based feed filtering:
    * /students reads from database/students.csv
    * /teachers reads from database/teachers.csv
    * /staff reads from database/staff.csv
    * Role badges displayed conditionally (is_user, is_prof, is_staff)

- Post interactions (like & repost):
    * Fetch post by ID → increment counter → save back to file
    * /updatepost?action=1&id=5 — like post #5
    * /updatepost?action=2&id=5 — repost post #5
    * Redirects to home page after update

- Profile page (/profile/<handle>):
    * Accepts username as URL parameter (auto-prepends @ if missing)
    * Looks up user via getuserprofile() — searches by handle
    * Displays: name, handle, bio, location, link, follower/following counts,
      post count, join date, verification badge
    * Own profile detection: is_own_profile = true if viewer = owner
